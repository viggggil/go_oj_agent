# Agent Eval 设计

## 数据集

管理员上传 UTF-8 JSONL 数据集。每个 Case 有稳定 id、类别、标题、user/assistant 多轮输入、受控 fixture 和 expectations。fixture 只能引用部署配置中的专用普通用户别名以及经过校验的题目、提交和语言字段，不能携带管理员身份或任意 user_id。

数据集保存于 Agent 自有数据库，上传时校验大小、角色、重复 id、JSON 数值和字段白名单。评测页面提供分页浏览、单独的数据集上传和样例查看；原始数据只对管理员 Eval API 可见。

## 运行流程

```text
选择数据集和被测 Agent
  → 固定 Agent/Prompt/Skill/Model/Provider/RAG 版本
  → 每个 Case 建立独立 eval 会话
  → 逐轮调用普通 RunService
  → 保存回答、工具摘要、知识证据和程序检查
  → 通过程序门禁的结果交给 eval_reviewer
  → 管理员查看结果、人工评分或重跑不可用评审
```

评测会话的 purpose 与普通 chat 隔离。每个重复次数使用新会话；Case 中后续 user turn 使用 Runtime 实际产生的历史，上传的 assistant turn 只作为参考，不注入模型上下文。单个 Case 失败不阻塞其他 Case，运行完成只表示执行结束，不等于质量通过。

## 程序化评分

程序检查扫描实际回答和实际运行摘要：要求的事实、工具、证据是否出现，禁止工具/主张/泄露是否命中，是否发生硬失败，工具和 RAG 是否真的执行。回答、检查、模型摘要和错误码保留在结果详情；列表接口只返回有界预览和状态。

## 模型评审

每次新评测自动固定专用 `eval_reviewer` Agent。该 Agent 无工具、无知识库、固定评审 Prompt/Skill 和 `deepseek-v4-pro` 模型，只接收有界用户问题、回答、程序检查和脱敏工具/知识摘要。模型必须返回一个严格 JSON，包含任务完成度、技术正确性、证据支持、指令遵循和清晰度五个 0–4 分维度，以及 hard_fail、违规和理由。

调用失败、超时、身份不匹配、JSON 多余字段或 case_id 不匹配都会记录为 UNAVAILABLE，不能计为通过。管理员可以在结果详情中按 expected_attempt 单条重跑；重跑使用保存的评审配置快照，不跟随当前配置漂移。人工评分单独保存并审计，不能覆盖硬失败。

## 隔离与资源限制

Runner 有最大挂起运行数、Case 并发和评审并发限制。每个 Run 有取消版本和请求幂等键；重复请求复用原 Run，不同正文使用同一请求编号会返回冲突。评测运行不会触发普通会话摘要，也不会出现在普通用户聊天历史中。

## 质量解读

建议同时观察程序通过率、hard failure、模型评审通过率、五维平均分、RAG evidence 命中率、工具错误率、延迟和不可用率。单一总分不能代替样例复核；遇到证据不足、引用错误、越权主张或多轮上下文丢失，应回到具体 Case 和工具轨迹定位。
