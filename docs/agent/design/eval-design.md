# Agent Eval 设计

## 数据集

管理员上传 UTF-8 JSONL 数据集。每个 Case 有稳定 id、类别、标题、user/assistant 多轮输入、受控 fixture 和 expectations。fixture 只能引用部署配置中的专用普通用户别名以及经过校验的题目、提交和语言字段，不能携带管理员身份或任意 user_id。

数据集保存于 Agent 自有数据库，上传时校验大小、角色、重复 id、JSON 数值和字段白名单。评测页面提供分页浏览、单独的数据集上传和样例查看；原始数据只对管理员 Eval API 可见。

## 运行流程

```text
选择数据集和被测 Agent
  → 固定 Agent/Prompt/Skill/Model/Provider/RAG 版本
  → 每个 Case 建立独立 eval 会话
  → 逐轮调用普通 RunService
  → 保存回答、工具摘要、知识证据和执行检查
  → 执行完成且无禁止动作的结果交给 eval_reviewer
  → 管理员查看结果、人工评分或重跑不可用评审
```

评测会话的 purpose 与普通 chat 隔离。每个重复次数使用新会话；Case 中后续 user turn 使用 Runtime 实际产生的历史，上传的 assistant turn 只作为参考，不注入模型上下文。单个 Case 失败不阻塞其他 Case，运行完成只表示执行结束，不等于质量通过。

## 执行检查与语义评分

程序只检查执行是否完成、运行错误和实际发生的禁止动作；它不再扫描回答文本寻找关键词，也不把指定工具名或证据标题当作自动通过条件。题目事实、算法正确性、任务完成度、表达和用户要求由模型评审给出语义评分，管理员可在结果详情中人工复核并保存评分。新的执行结果在模型评审或人工评审前显示“待评审”，不会因为执行成功被算作质量通过；历史结果继续按原评分规则展示。

模型评审会检查完整回答，包括变体和补充示例，支持同义表达、符号和变量名变化；输入超限时保留回答开头和结尾并标记已截断。评审失败属于“不可用”，可以单独重跑，不能折算成通过。

## 回答与阶段进度

普通助手在每次模型响应中先生成简短的公开阶段摘要，服务将 `<progress>...</progress>` 前缀从正文分离。每个完成的 reason 节点发送一条 `reasoning_summary`，前端按生成顺序将摘要直接显示在同一条助手消息中、最终答案之前，不折叠且不加阶段编号；摘要缺失或含内部信息时使用阶段状态兜底。不读取原始推理内容，摘要不进入最终答案或持久化的问答历史。正式回答直接解释题目和结论，不描述数据库、知识检索或内部工具的使用过程。

聊天界面同时保留准备、分析、工具调用、调用结果和整理回答等运行状态，以浅色小字按事件顺序穿插在公开摘要与最终答案之间，不使用折叠列表。摘要使用正文颜色且不带阶段编号，运行状态不进入最终回答正文。

## 模型评审

每次新评测自动固定专用 `eval_reviewer` Agent。该 Agent 无工具、无知识库、固定评审 Prompt/Skill 和 `deepseek-v4-pro` 模型，只接收有界用户问题、回答和脱敏执行证据。模型必须返回一个严格 JSON，包含任务完成度、技术正确性、证据支持、指令遵循和清晰度五个 0–4 分维度，以及 hard_fail、违规和理由。评审提示特别要求检查补充结论中的实质错误，并将通用知识的可核验推理与平台特有题目事实分开判断。

调用失败、超时、身份不匹配、JSON 多余字段或 case_id 不匹配都会记录为 UNAVAILABLE，不能计为通过。管理员可以在结果详情中按 expected_attempt 单条重跑；重跑使用保存的评审配置快照，不跟随当前配置漂移。人工评分单独保存并审计，不能覆盖执行失败或硬失败。

## 隔离与资源限制

Runner 有最大挂起运行数、Case 并发和评审并发限制。每个 Run 有取消版本和请求幂等键；重复请求复用原 Run，不同正文使用同一请求编号会返回冲突。评测运行不会触发普通会话摘要，也不会出现在普通用户聊天历史中。

## 质量解读

建议同时观察执行成功率、hard failure、模型评审通过率、五维平均分、人工复核通过率、工具错误率、延迟和不可用率。单一总分不能代替样例复核；遇到证据不足、引用错误、越权主张或多轮上下文丢失，应回到具体 Case 和工具轨迹定位。
